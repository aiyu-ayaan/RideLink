# RideLink

RideLink is an Android companion app for TVS scooters with a SmartXonnect Bluetooth display
(Ntorq 125, Ntorq XT, Race XP, 2025+ Ntorq). It replaces the official TVS Connect app for the
riding features: it connects to the scooter display over BLE, shows Google Maps turn-by-turn
directions on it, forwards incoming calls, and keeps the display's clock, phone battery and
signal up to date. No TVS account or server is needed.

The BLE protocol was recovered from TVS Connect 8.13.2. `PROTOCOL.md` is the source of truth
for every byte the app sends. Personal-use project: never ship TVS code, assets or branding.

## Stack

Native Android, Kotlin, Jetpack Compose. Package `com.aiyu.ridelink` (debug: `.debug` suffix).
Build setup mirrors `../Findex` (AGP 9.4, Kotlin 2.4, Compose BOM 2026.08, Material3 1.5 alpha, Hilt, KSP).

Modules:

- `app` => entry point: `MainActivity`, `RideLinkApp`, and the Android services
  (`ClusterService` foreground service, `RideNotificationListener` + `MusicWatcher`, `BootReceiver`).
- `core` => no UI. `protocol/` (frame encoder, models, turn/weather tables, `DisplayTelemetry` parser),
  `ble/ClusterLink` (GATT), `ClusterController` (ride session logic), `nav/MapsNotificationParser`,
  `notify/SocialNotificationParser`, `weather/WeatherRepository` (Open-Meteo + coarse location + Geocoder),
  `phone/CallControl` (TelecomManager), `display/DisplayTemplate` (live custom lines), `settings/` (DataStore),
  `analytics/` (`RideMath` pure stats, `RideRecorder` auto-records rides, `RideStore` framework SQLite).
- `ui` => all Compose screens, theme, and **all strings** (`ui/src/main/res/values/strings.xml`).
  `core` and `app` hold no user-facing strings; the app module reads them via `com.aiyu.ridelink.ui.R`.

`tools/` holds desktop test tools (system Python with python3-dbus + gi):
- `fake_cluster.py` emulates the scooter display over BlueZ and decodes every frame it receives.
- `central_test.py` plays the phone from a second adapter and writes the pinned test frames.

## How it works

1. Pair: scan for BLE names containing `TVS` (not `HUD`). Every paired scooter is saved in `GarageStore`
   (SQLite, own model per bike); the selected one is copied to DataStore (`deviceAddress`, `model`),
   so the service and boot paths see one bike. Settings -> Scooter switches, adds and removes bikes.
2. Auto-connect: once a scooter is paired and Bluetooth is granted, `RideLinkRoot` starts
   `ClusterService` (foreground, `connectedDevice`) on app start, after pairing, and `BootReceiver` on boot.
   The service calls `ClusterController.start()`. The Ride button is Disconnect / Connect.
3. `ClusterLink` connects, requests MTU 512, enables notify on `5354`, then writes on `5352`
   with response, one frame at a time. On drop it reconnects with `autoConnect = true`.
4. On ready: rider name, social counts and music frames, then the `5B 4A` status frame every 2 s
   and (TFT models) weather + AQI + place name every 15 min.
5. `RideNotificationListener` turns Google Maps notifications into `NavStep`s
   (nav text frame, 400 ms gap, nav control frame), call notifications into a caller frame
   repeated every 500 ms while ringing, and WhatsApp/Facebook/Instagram notifications into `5B 9C`
   counts. `MusicWatcher` follows the active media session (`5B 62/63/60`).
6. Frames from the display are logged and folded into `DisplayTelemetry` (speed, odometer, trip, fuel,
   range, speeds, mileage). A change of `5A 10` byte 12 accepts/rejects the ringing call. Also used for
   Auto model detection.
7. Every TFT feature has a Settings toggle. Runtime grants: Bluetooth (required), notification access,
   and the optional READ_PHONE_STATE + ACCESS_COARSE_LOCATION + ANSWER_PHONE_CALLS card.

## Design

- Material 3 Expressive only: `MaterialExpressiveTheme`, `MotionScheme.expressive()`, dynamic color
  on Android 12+, red tonal-spot fallback scheme. See `development/docs/DESIGN_SYSTEM.md`.
- Brand: "Closed loop" mark (ring + spark), RideLink Red `#B3261E`, Spark Amber `#FFB82E`, Ink `#1C1B1F`.
  `development/brand/BRAND.md`; every logo file and Android icon/splash drawable is generated by
  `development/brand/logo_geometry.py` (edit the script, then re-run it). Splash: AndroidX SplashScreen,
  `Theme.RideLink.Starting`, animated icon + exit in `MainActivity.playSplashExit`.
- Bottom navigation with four tabs: Ride, Analytics, Settings, Console. No drawer.
- Analytics: period picker, one hero number (distance + change), stat tiles, Canvas charts in `ui/analytics/Charts.kt`
  (single series, primary marks, tertiary selection, tap/drag readout, no dual axis), records, ride list, ride sheet.
- Ride screen: hero status card (cookie shape, `LoadingIndicator` while searching), turn-arrow
  dashboard (big arrow, distance, ETA, left, speed), ride data card, vehicle card, weather card, music card, call card,
  one primary button (Connect / Disconnect). New cards live in `ui/ride/RideCards.kt`.
- Console is a real tool, not a debug leftover: manual text, test turn, test call, demo ride, one chip per TFT
  frame (weather, location, chat counts, music, default screen), frame log.

## Conventions

- Compose only, `androidx.compose.material3` 1.5 alpha (Expressive opt-ins set in Gradle).
- Colors only through `MaterialTheme.colorScheme` roles. No raw `Color(0x…)` in screens
  (the fallback scheme in `ui/theme/Theme.kt` is the one exception).
- Spacing through `Dimens`; shapes through `MaterialTheme.shapes` / `MaterialShapes`.
- Motion through `MaterialTheme.motionScheme` specs, never ad-hoc `tween` durations.
- Settings live in DataStore (`core/settings`). Nothing list-like in DataStore: ride history is SQLite (`RideStore`).
- All BLE writes go through `ClusterController.send` -> `ClusterLink.send` (queued, with response).
  Never write GATT from UI code.
- Long-lived work (the ride session) runs in `ClusterService`, never on a ViewModel scope.
- `shortcut:` comments mark known limits; list them before releases.

## Commands

- Unit tests: `./gradlew :core:testDebugUnitTest`
  (protocol, nav, social and telemetry tests are pure Kotlin; they also run in a plain Kotlin/JVM project
  when the Android SDK is not available)
- Build: `./gradlew :app:assembleDebug`
- Run on emulator/device: `./run.sh` (`--logs` to follow logcat)
- Fake display (needs a BLE adapter): `/usr/bin/python3 tools/fake_cluster.py --adapter hci0`
- End-to-end BLE check (two adapters): run the fake on hci0, then
  `/usr/bin/python3 tools/central_test.py --adapter hci1`

## Testing without the scooter

1. Console -> Demo ride: fake route, speed and call through the real encoder (UI + frames).
2. `fake_cluster.py` on this PC + the app on a real phone: pair with `TVSBT01`, every frame is decoded
   and logged to `captures/`. Type hex into the fake's stdin to send frames back (e.g. `5a 10 00 3e …`).
3. The Android emulator has no host Bluetooth passthrough; BLE tests need a real phone.
